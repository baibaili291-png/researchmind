# 架构说明

## 分层

```
┌─────────────────────────────────────────────────────┐
│  前端  静态 HTML/JS（零依赖）  或  React + TypeScript │
└────────────────────┬────────────────────────────────┘
                     │ HTTP + SSE
┌────────────────────▼────────────────────────────────┐
│  API    backend/api/app.py (FastAPI)                 │
│         backend/api/server.py (零依赖等价实现)        │
│         backend/api/service.py (后台 worker + 事件)   │
└────────────────────┬────────────────────────────────┘
                     │
┌────────────────────▼────────────────────────────────┐
│  编排    backend/core/graph.py  带环状态机            │
│         plan → search → fetch → extract → verify     │
│              ↑                          │           │
│              └──── follow_up_queries ────┘           │
│                    → write → cite                    │
└──────┬──────────────┬──────────────┬─────────────────┘
       │              │              │
┌──────▼─────┐ ┌──────▼──────┐ ┌─────▼──────┐
│ providers/ │ │ core/verify │ │ core/ledger│
│ 真实检索链  │ │ 确定性校验   │ │ 证据账本    │
└────────────┘ └─────────────┘ └────────────┘
```

## 默认即真实研究（无需 API key）

与常见"必须先配 key 才能跑"的设计不同，本项目**默认就走真实联网研究**：

| 环节 | 无 key 时的实现 | 有 key 时 |
|---|---|---|
| 规划 | 维度模板规划器：从问题中识别主题/年份/用户指定章节，按 7 个研究维度生成查询 | LLM 拆解 |
| 搜索 | 免密钥引擎链：so.com → Bing News RSS | Tavily 优先 |
| 抓取 | HTTP + 自研 readability 正文提取，失败降级 Playwright → Reader API | 同左 |
| 抽取 | 确定性句子打分：数字密度 + 主题命中 + 事实动词 | LLM 结构化输出 |
| 写作 | 确定性渲染：只从证据账本组稿 | LLM 撰写 |

因此 `python -m backend.api.server` 开箱即产出**基于真实网页**的报告。

## 关键数据流

1. 用户问题 → `planner.analyze_topic` 提取主题与年份 → 生成 7 个维度的子问题与查询。
2. `search` 逐查询调用引擎链，结果按 URL 规范化去重；命中缓存则跳过网络请求。
3. `fetch` **并发**抓取（`fetch_many`，默认 6 线程），每个域名仍按限流器保持间隔。
4. 正文经 readability 提取后过**两道质量闸门**：长度不足直接丢弃；主题不相关直接丢弃。
5. `extract` 按确定性打分选出含数字/事实动词的句子，引文是原文逐字节选。
6. `verify` 拒绝引文不在原文中的证据，并检测同主题数值冲突。
7. `route` 决定回退（冲突/缺口 → 生成追问重搜）或前进（→ 写作）。
8. `write` 仅用账本内证据组稿，每条事实带 `[E#]`；未覆盖维度写入"研究局限"。
9. `cite` 审计引用可解析性与覆盖率。
10. 全程通过 SSE 推送事件。

## 免密钥检索的工程现实（实测结论）

在本机网络环境下实测了所有免密钥入口，结论已固化为代码：

- **so.com（360）**：结果相关性最好，且 HTML 里带 `data-mdurl`（真实落地页 URL）与
  `data-result-summary`（摘要）。注意 `href` 是不透明 JS 跳转桩，必须用 `data-mdurl`。
- **限流是常态**：短时间十余次查询后 so.com 返回 6 KB 验证页，搜狗返回 3.8 KB 反爬页。
  对策是全局速率限制器 + 惩罚性退避（遇验证页退避 30s）+ 结果缓存复用。
- **Bing 网页搜索**：可达但相关性差，中文行业查询会返回日历/节假日页，不可用作主引擎。
- **Bing News RSS**：`format=rss` 常返回 HTML 外壳而非 feed，需按 `<rss`/`<?xml` 特征判定，
  不能只判断"以 `<` 开头"。
- **Google / DuckDuckGo / Wikipedia**：被出口代理拦截（502）。
- 因此引擎链顺序为：Tavily（若配 key）→ so.com → Bing News RSS。

## 为什么校验不用 LLM

- 确定性：同样输入永远同样输出，可单测、可回放。
- 零成本零延迟：不额外消耗模型调用。
- 可证伪：引文子串匹配要么通过要么不通过，不存在"看起来差不多"。

LLM 只负责生成候选事实；判定真伪由代码完成。这是整个系统可信度的基础。

## 已修复的真实缺陷（均由联网实测暴露）

| 缺陷 | 后果 | 修复 |
|---|---|---|
| 预算按"结果条数"而非"搜索次数"计数 | 7 个子问题一轮即撑爆预算，循环从未迭代，证据全部落到第一个章节 | `Budget.max_searches` 计数搜索调用，新增 `max_hits` 单独限制累积 |
| SERP 相对链接含原始中文与空格 | `urllib` 抛 `InvalidURL`，整轮研究崩溃 | `sanitize_url` 统一净化，非绝对 http(s) 链接直接丢弃 |
| 搜索引擎自身链接被当文章抓取 | 浪费预算，抓到的是另一个结果页 | `_INTERNAL_RE` 过滤 so.com/baidu/sogou 等自有域 |
| 千分位数字解析 | "400,000家" 被解析为 0.0 或 None | 正则优先匹配带逗号分组 + `parse_number` 去分隔符 |
| 正文提取失败时抽取无关内容 | 体育/娱乐标题被当作行业证据 | 主题相关性闸门 + 抽取硬门禁（无数字且无事实动词的句子不接受） |
| 主题提取丢失限定词 | "中国 AI Agent" 退化为裸词 "Agent"，查询失效 | 先剥离指令动词与研究维度词，再取头部名词短语 |
| 助词剥离误伤词汇 | "研究目的与意义" → "目与意义" | `strip_possessive` 先屏蔽"目的/的确/标的"等词内 的 |
